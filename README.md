# External Search Methods

## About

Practical Assignment for **BCC203** — Data Structures II at **UFOP** (Federal University of Ouro Preto). This project implements and compares four External Search methods for key search in files:

1. **Indexed Access** — separate index structure with a lookup table
2. **BST** — Binary Search Tree stored on disk
3. **B-Tree** — balanced tree structure with order M = 50
4. **B* Tree** — B-Tree variation with internal and external pages

## Build and Run

### Compile

```bash
make
```

### Run

```bash
./pesquisa <method> <quantity> <situation> <key> [-P]
```

### Parameters

| Parameter       | Valid values             | Description                          |
|----------------|-------------------------|--------------------------------------|
| `<method>`     | 1, 2, 3, 4              | Search method                |
| `<quantity>`   | Positive integer         | Number of items in the input file          |
| `<situation>`  | 1, 2, 3                 | File order (see below)               |
| `<key>`        | Non-zero integer         | Key to search for                    |
| `[-P]`         | Optional                 | Print file keys                      |

### File Situations

- **1** — Ascending file (sorted)
- **2** — Descending file
- **3** — Random file

> **Note:** Indexed Access (method 1) requires an ascending/sorted file (situation 1).

### Examples

```bash
./pesquisa 1 1000 1 500
./pesquisa 2 1000 2 500
./pesquisa 3 1000 3 500 [-P]
```

```bash
make run       # Compile and run

```

## Performance Metrics

For each search, the program displays:

- **Number of transfers** — how many disk blocks were read
- **Number of comparisons** — how many keys were compared
- **Execution time** — time in seconds

## Benchmark

The project includes a benchmark module that runs multiple searches and reports the average metrics:

```bash
./pesquisa <method> <quantity> <situation> <key>
```

## Test Results

Tests were conducted on the following machine:

- **Processor:** Ryzen 5 4600G
- **RAM:** 16GB
- **OS:** Fedora Linux 43 (KDE Plasma Desktop Edition) x86_64

For each method, 10 searches were performed and averaged. The key for test `i` was calculated as: `key_i = i * (total_items / num_tests)`, ensuring equal spacing between keys.

### Indexed Access

| Items     | Comparisons | Transfers | Time (s) |
|-----------|-------------|-----------|----------|
| 100       | 13.1        | 3.0       | 0.000061 |
| 1,000     | 23.0        | 21.0      | 0.000096 |
| 10,000    | 122.0       | 201.0     | 0.005972 |
| 100,000   | 1,112       | 2,001.0   | 0.052606 |
| 1,000,000 | 11,012      | 20,001.0  | 0.546785 |

For descending order, results were similar: 1M items in 0.51s with 9,012 comparisons. The method is fastest overall but requires sorted files.

### Binary Search Tree (BST / ABB)

| Items     | Comparisons | Transfers | Time (s) |
|-----------|-------------|-----------|----------|
| 100       | 574.6       | 670.0     | 0.014340 |
| 1,000     | 10,981.8    | 11,976.0  | 0.076753 |
| 10,000    | 153,685.2   | 163,676.4 | 0.828786 |
| 100,000   | 2,042,328.8 | 2,142,319.2 | 10.317514 |
| 1,000,000 | 25,250,935.8 | 26,250,921.2 | 335.184127 |

Ordered files caused the tree to degenerate into a linked list (1M items took over 8 hours — infeasible). Random files yielded reasonable times. Without balancing (AVL, Red-Black), BST is only practical for unsorted data.

### B-Tree

| Items     | Comparisons | Transfers | Time (s) |
|-----------|-------------|-----------|----------|
| 100       | 5,301       | 100.0     | 0.000245 |
| 1,000     | 86,263.9    | 1,000.0   | 0.007686 |
| 10,000    | 1,427,219.4 | 10,000.0  | 0.080774 |
| 100,000   | 17,314,031.8 | 100,000.0 | 0.911601 |
| 1,000,000 | 227,352,892.5 | 1,000,000.0 | 17.505913 |

Descending order was slightly faster (14.46s for 1M items). Transfers are linear O(n) since every record must be read during tree construction. The balanced structure ensures stable performance regardless of file order.

### B* Tree

| Items     | Comparisons | Transfers | Time (s) |
|-----------|-------------|-----------|----------|
| 100       | 5,303       | 100.0     | 0.001296 |
| 1,000     | 87,193.8    | 1,000.0   | 0.009723 |
| 10,000    | 1,439,742.3 | 10,000.0  | 0.090832 |
| 100,000   | 17,418,280.7 | 100,000.0 | 0.877685 |
| 1,000,000 | 228,280,821.4 | 1,000,000.0 | 16.052918 |

B* showed a slight advantage over B-Tree in execution time across all cases (16.05s vs 17.51s for 1M ascending items). Descending files again performed best. Transfer costs remained linear.

## Conclusions

- **Indexed Access** is the fastest method for sorted files, with the lowest comparison count and execution time (under 1 second for 1M records). Its limitation is requiring pre-sorted data.

- **External BST** performed the worst on ordered files due to tree degeneration into a linked list. It is only viable for unsorted data, and would benefit from a balancing mechanism such as AVL or Red-Black trees.

- **B-Tree and B* Tree** demonstrated superior performance over BST by maintaining a balanced structure with controlled growth. Both handle large datasets efficiently.

- **B* Tree** outperformed the traditional B-Tree in execution time across nearly all test scenarios, thanks to its separation of internal and external pages.

- **Transfer counts** for B-Tree and B* are linear O(n) because every record must be read once during tree construction.

- **Descending-ordered files** consistently yielded the best results for both B-Tree and B*, while random files had slightly higher costs.

- **Indexed Access** offers the best performance-to-cost ratio for sorted files, while **balanced trees (B/B*)** are more suitable for applications involving large volumes of data where sorted order cannot be guaranteed.
